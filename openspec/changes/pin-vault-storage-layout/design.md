# Design — pin-vault-storage-layout (issue #148)

## Context

The repo already has a two-layer layout-pinning pattern; this change adds
`SyndicateVault` to it, inventing nothing:

1. **CI layer** — `script/check-layout-goldens.sh` runs
   `forge inspect <Contract> storageLayout --json`, canonicalizes it
   (`canonical_layout`), and diffs against a committed golden JSON. Runs in CI
   at `.github/workflows/ci.yml:166` ("Layout goldens" step). Regeneration is
   `./script/check-layout-goldens.sh --update-golden`, committed in the same
   PR as the storage change.
2. **forge-test layer** — raw `vm.load` slot pins
   (`test/GuardianRegistryLayoutPins.t.sol`,
   `test/governor/GovernorLayoutPins.t.sol`) so a reorder fails under plain
   `forge test` even when the shell script isn't run.

Both layers exist for governor/factory/registry/StakedWood. Neither exists
for the vault. The implementer's job is transcription: this document
enumerates the schema, the full field list, the exact wiring, and the test
shape.

## Golden format (read from the checker — do not re-derive)

`check_contract <Name> <golden-path>` compares the output of
`canonical_layout <Name>` (script lines 67-165) against the golden file.
The canonical JSON has exactly two top-level keys:

- `"storage"` — array, ORDER-SIGNIFICANT, one entry per top-level state
  variable in slot order: `{"label": <name>, "slot": "<decimal string>",
  "offset": <int>, "type": <normalized type>}`. Note `slot` is a STRING,
  `offset` an integer (forge's own convention, preserved).
- `"types"` — object, alphabetically sorted, one entry per STRUCT reachable
  transitively from the storage variables (through mapping values and array
  bases); each maps the normalized struct type to its member list in the same
  `{label, slot, offset, type}` shape. Non-struct types carry no entry.

Type normalization (the `norm()` function): solc AST ids are stripped
(`t_struct(AgentConfig)1234_storage` → `t_struct(AgentConfig)_storage`) but
ARRAY LENGTHS are preserved (`t_array(t_uint256)28_storage` stays intact — a
gap resize with no other change must diff). See
`script/guardian-registry-layout.golden.json` for a complete worked example
of the shape.

The golden is NEVER hand-written. It is generated by the checker itself (see
"Generation" below); this document's layout table exists so the implementer
can VERIFY the generated output, not author it.

## Generation (the only forge work in this change)

Run ONCE during implementation, AFTER the wiring line is added to the script,
under the repo's build-lock discipline (foreground, generous timeout,
serialized behind `while pgrep -x forge >/dev/null; do sleep 30; done` or a
PID-carrying mkdir lock — this repo's `via_ir` builds OOM-kill each other
when run concurrently):

```
./script/check-layout-goldens.sh --update-golden
```

This is the same command every other golden was produced by. It rewrites ALL
goldens; correctness check: `git status`/`git diff` must show exactly ONE new
file (`script/syndicate-vault-layout.golden.json`) and ZERO modifications to
the five existing goldens. Any diff in an existing golden means the working
tree's layout has drifted from `main` — stop and investigate before
committing. Then run the checker plain (`./script/check-layout-goldens.sh`)
and confirm it exits 0 with the new OK line.

Do NOT hand-run `forge inspect SyndicateVault storageLayout --json` and paste
the raw output into the golden: the checker canonicalizes (strips AST ids,
prunes non-struct types, re-indents), so raw forge output will never diff
clean.

## Wiring into check-layout-goldens.sh

Three edits, all comments-plus-one-line:

1. Header comment (lines 2-3): the script self-describes as guarding "the
   beacon/proxy-upgraded governance contracts (SyndicateGovernor,
   SyndicateFactory, GuardianRegistry)" — already stale (StakedWood was added
   without updating it). Rewrite the parenthetical to name all five,
   including SyndicateVault.
2. Add, after the `check_contract StakedWood ...` call (line 229), a comment
   block plus the call, matching the per-contract commentary convention the
   other four have:

   ```
   # SyndicateVault is UUPS (upgrades factory-gated) and is the contract that
   # CUSTODIES LP ASSETS — a layout break here is fund-loss on the first
   # upgraded live proxy, not a bricked parameter. Pinned before any mainnet
   # vault exists (issue #148; owner confirmed no live vault proxy), so this
   # golden is the FIRST baseline, not a re-baseline. From the first real
   # deploy onward the layout is frozen and every change must be append-only
   # (carved from the front of __gap) against this golden. In-test twin:
   # test/VaultLayoutPins.t.sol.
   check_contract SyndicateVault script/syndicate-vault-layout.golden.json
   ```

3. Final OK echo (line 232): extend the contract list to include
   SyndicateVault so the success line stays truthful.

## test/VaultLayoutPins.t.sol

Transcribe the existing pattern (file-level natspec explaining WHY + layout
map; sentinel constants; `ERC1967Proxy` fixture; `_slot(uint256)` helper via
`vm.load`; positive pins). Name and location follow
`test/GuardianRegistryLayoutPins.t.sol` (vault tests live at `test/` root:
`test/SyndicateVault.t.sol`). Contract name: `VaultLayoutPinsTest`.

Fixture: deploy an `ERC20Mock` asset (as `test/SyndicateVault.t.sol` does),
`new SyndicateVault()` impl, wrap in `ERC1967Proxy` with
`SyndicateVault.initialize(InitParams)` (`ISyndicateVault.sol:75-84`:
asset, name, symbol, owner, executorImpl, openDeposits, agentRegistry,
managementFeeBps). The TEST CONTRACT is `msg.sender` at initialize, so it
becomes `_factory` — the same trick GovernorLayoutPins uses — unlocking the
factory-gated `setWithdrawalQueue`. Use distinct sentinel constants per
field, per the existing files.

Pins, by slot (positive writes wherever a write path is cheap; `vm.store` +
public getter — a REVERSE pin, equally binding — where the only honest write
path needs a full governor lifecycle; JSON-golden-only where neither exists):

- **Slots 3, 6, 7, 8, 9, 10 (init-written prefix)** — one view test:
  `_slot(3)` = executorImpl sentinel; `_slot(6)` = packed word
  `uint256(openDeposits ? 1 : 0) | (uint256(uint160(agentRegistry)) << 8)`
  (bool at offset 0, address at offset 1); `_slot(7)` = managementFeeBps
  sentinel; `_slot(8)` = address(this) (factory); `_slot(9)` = the executor
  sentinel's `.codehash`; slot 10 low byte = the mock asset's decimals.
- **Slot 10 packing (`_withdrawalQueue` at offset 1)** — call
  `setWithdrawalQueue(QUEUE_SENTINEL)` as factory, then assert the FULL
  slot-10 word equals `uint256(decimals) | (uint256(uint160(QUEUE_SENTINEL)) << 8)`
  — pins both the queue's slot and its offset relative to
  `_cachedDecimalsOffset`.
- **Slot 12 (`_agentFeeBpsPlusOne`)** — owner calls `setAgentFeeBps(777)`,
  assert `_slot(12) == 778` (pins the slot AND the offset-by-one encoding).
- **Slot 13 (packed `minBufferBps`/`minHoldingPeriod`/`instantExitFeeBps`)** —
  owner sets `setMinBufferBps` and `setInstantExitFeeBps`, then assert the
  FULL word equals `uint256(minBuffer) | (uint256(instantExitFee) << 48)`.
  `minHoldingPeriod` has no setter, but pinning `instantExitFeeBps` at BIT
  offset 48 (byte offset 6) transitively pins the uint32 occupying bytes 2-5:
  if `minHoldingPeriod` were removed or retyped, `instantExitFeeBps` would
  repack and the word changes.
- **Slots 14, 18, 19 (fee/flow block — reverse pins)** — these are written
  only mid-proposal-lifecycle; a forward pin would drag in a full governor
  fixture, which is over-engineering for a layout test. Instead `vm.store` a
  sentinel and assert the PUBLIC GETTER decodes it: slot 14 →
  `interimNetFlow()` (`SyndicateVault.sol:1393`); slot 18 →
  `highWaterPricePerShare()` (`:1537`); slot 19 → store one composite word
  (mgmt sentinel in the low 128 bits, perf sentinel in the high 128) and
  assert `crystallizedMgmt()` (`:1583`) and `crystallizedPerf()` (`:1588`)
  each return their half — pinning both slot and intra-slot offsets.
- **Slots 0/1 and 4 (sets + agents mapping)** — `approveDepositor(sentinel)`
  then assert `_slot(4) == 1` (AddressSet `_inner._values` length lives at
  the struct's first word); `registerAgent` (using the repo's
  `MockAgentRegistry`) then assert `_slot(1) == 1` and read
  `_agents[agent].agentId` through the derived slot
  `keccak256(abi.encode(agent, uint256(0)))` (mapping-base technique from
  GuardianRegistry's `vaultOf` pin).
- **Slot 20 (`__gap[0]`)** — after the slot-19 sentinel store (field above
  WIRED, per the GuardianRegistry M7 lesson: a gap-zero check over a
  never-populated neighbor guards nothing), assert `_slot(20) == bytes32(0)`.
- **Golden-only** (deep write paths, no getter): `_laneALockPid` (11),
  `lastDepositAt` (15), `_mgmtAssetSeconds` (16), `_mgmtBase`/`_mgmtLastUpdate`
  (17). State this explicitly in the file's natspec so nobody mistakes the
  omission for an oversight — the JSON golden pins their label/slot/offset/
  type field-by-field.

File-level natspec must carry the layout map (the table above, condensed to
the two-column style of the existing files) and the append-only rule: new
fields are carved from the FRONT of `__gap`, add a pin, never edit one.

## Sequencing vs. retire-lane-a (#54) — RECOMMENDATION: land BEFORE it

`retire-lane-a` (branch `chore/retire-lane-a`, spec complete, implementation
not started) deletes vault storage outright — its task 2.6: `__gap`
`uint256[28]` → `uint256[31]`, freeing `_laneALockPid`, `_interimNetFlow`,
and `_crystallizedMgmt`+`_crystallizedPerf` (its packed `instantExitFeeBps`
removal frees no slot) — legal only because no vault proxy is live.

Two orderings were weighed:

- **AFTER #54**: the golden is generated once against the post-deletion
  layout and never churns. Cheaper on paper.
- **BEFORE #54** (recommended): the pin exists WHILE the largest
  storage-touching change in flight is implemented. #54's whole risk profile
  is "vault storage surgery with no automated layout signal" — landing the
  net after the trapeze act defeats the purpose for the one change that
  motivated this issue. When #54 lands, it trips the golden and the pin test
  BY DESIGN, and re-baselines both via the already-documented ceremony
  (`--update-golden` + pin-test edit in the same PR — precedent: the
  governor's PR #56 re-baseline and the DPoS-removal re-baselines, both
  recorded in the checker's comments). That forced, visible diff is the gate
  WORKING: it converts "deletion silently shifts nine fields" into "deletion
  produces a reviewed golden diff". The churn cost is one regenerated JSON
  and a mechanical test edit; the benefit is that the highest-risk in-flight
  change executes under the guard. This change is also small and ready now,
  while #54 is a ~250-line task list that hasn't started — "before" costs no
  calendar time.

Fallback: if #54 merges first anyway, regenerate the golden and re-derive the
pin table against the post-deletion layout before implementing (tasks.md
carries a pre-flight check for this).

#54's tasks.md should gain a note (in ITS OWN PR, when rebased) that task 2.6
now also regenerates `script/syndicate-vault-layout.golden.json` and updates
`test/VaultLayoutPins.t.sol` — do not edit the retire-lane-a branch from this
change.

## CI cost

Zero new machinery. The "Layout goldens" step (`.github/workflows/ci.yml:166`)
already runs `./script/check-layout-goldens.sh`; the addition is one more
`forge inspect` against an already-built artifact tree (the script's single
`forge build` is shared) — seconds. `test/VaultLayoutPins.t.sol` rides the
normal `forge test` job like the two existing pin files.

## Alternatives considered

- **Placeholder convention for removed fields** (issue #148's suggested scope
  item 3: `__deprecated_x` same-slot placeholders). Deliberately NOT adopted
  here: while no proxy is live, outright deletion + golden re-baseline is the
  repo's established practice (StakedWood, GuardianRegistry precedents), and
  `retire-lane-a` already encodes the placeholder rule for the one live
  pinned lineage it touches (factory slot 7). Adopting a blanket convention
  belongs to the upgrade-discipline docs at first mainnet deploy, not to this
  additive change.
- **Pinning `SyndicateVaultAdminLib` / `BatchExecutorLib`**: both are
  stateless delegatecall libraries operating on storage references passed in
  — no linear layout of their own to pin; the checker's empty-layout guard
  would (correctly) refuse them.
