## Why

**Tier 2 prices arbitrary calldata but cannot reach it.** `tierOf` returns `(2, 10_000)` for any uncertified pair — "arbitrary calldata at full notional" — yet `SyndicateVault._guardBatchCalls` PART 2a refuses any callee that is not `asset()` or `isAdapterAllowed(target)`, and that gate is tier-blind. So an uncertified target is not expensive, it is unreachable: the full-notional price is decorative for exactly the calls it was written for. Every new venue a proposer wants to route to costs an owner transaction on the TierRegistry multisig, which makes the strategy surface permissioned in practice even though proposing is permissionless.

**The gate cannot simply be deleted, and the reason is worth stating precisely.** Governor batches run under `delegatecall`, so every sub-call reaches its target carrying `msg.sender == vault`. The per-call meter in `BatchExecutorLib` sees only the vault's own `asset()` balance delta, so *authorization-granting* calldata — `approve(attacker, max)`, ERC-777 `authorizeOperator`, ERC-721 `setApprovalForAll`, any unenumerated router's approval shape — moves zero, meters zero, prices zero coverage, and drains in a later transaction. `cap_i` cannot bound it because the loss does not land in the metered transaction. This is the same unenumerable-selector class that defeated four consecutive audit rounds (issue #115 / PR #157 rounds 1-4, issue #18), and it is why the durable fix was a target allowlist rather than a price. `SyndicateGovernor._snapshotTierAndGate` already concedes the residual in-source: "a metering-SCOPE question about what the meter can see."

**Isolating the caller resolves both at once.** If arbitrary calls execute from a per-proposal clone holding only the capital it was funded with — rather than from the vault under `delegatecall` — then the callee's identity stops mattering. It receives `msg.sender == clone`, reaches no vault allowance, no vault-held position token, and no `msg.sender == vault` gate. Maximum loss becomes structural (`sum(cap_i)` funded in) instead of measured, which is precisely the figure tier-2 coverage already charges for. The owner ceremony collapses from "every target, forever" to "one template class, once."

## What Changes

- **New protocol-owned sandbox contract**, minted by the vault itself. `SyndicateVault` carries the sandbox implementation address as an immutable and clones it per proposal via CREATE2. It is not a `StrategyFactory` template, carries no TierRegistry entry, and requires no owner ceremony of any kind — it is protocol code on the same footing as the withdrawal queue.
- **New `onlyGovernor` vault entry point** that deploys the sandbox, transfers the declared funding to it, and dispatches its stored calls. Funding is metered against `effectiveMaxCapital` exactly like a batch outflow.
- **Arbitrary targets require no TierRegistry entry and no owner action.** Targets named inside the sandbox's calls are never consulted against `isAdapterAllowed`, because they are never batch callees. The proposer chooses them at propose time; **guardians review them before approving**, which is the only gate.
- **`SyndicateVault._guardBatchCalls` is NOT modified and is NOT consulted** for sandbox calls. PART 1, 1b, 2a and 2b keep running verbatim on the governor batch; the sandbox path is a separate, governor-gated entry point, so no exemption is carved into the batch guard.
- **The sandbox call set becomes first-class proposal data**, stored alongside `executeCalls` and readable on-chain before the guardian approval vote — the review artifact the coverage quorum is deciding on.
- **A funding ceiling that is effective rather than inert.** `tier2CallCapBps()` currently defaults to `10_000` (100% of TVL — no bound). The sandbox SHALL read the live ceiling and bound its own funding at execute time, so a ceiling tightened after propose still binds. Enforced by the sandbox rather than by a governor change, deliberately: the propose-time `Tier2CallCapExceedsCeiling` check lives in the unarchived `per-call-capital-declarations` change, and stacking a `syndicate-governor` delta on unmerged work would couple two changes that can land independently.
- **Guardian quorum stays mandatory** at every tier (`quorumTierThreshold = 0`, unchanged). A sandbox proposal with non-zero coverage always needs stake-backed approvers; under-raised coverage scales `effectiveMaxCapital` and every per-call cap down pro-rata, as today.
- **Privileged-address denylist inside the sandbox.** The clone SHALL refuse to call the vault, the withdrawal queue, the governor, the TierRegistry, the ExposureLedger, WOOD or sWOOD. Not a fund-safety bound (the cap already is one) but an accounting one — a clone holding vault capital could otherwise mint vault shares mid-proposal while deposits are locked.
- **Residue integration**: the clone SHALL implement `IStrategyDelivery`. Arbitrary calls can end holding a token the clone cannot value, so `hasUnvaluedResidue()` returns true whenever it holds a non-asset balance at settle — which locks deposits until `collectResidue` clears it. **This is a real and intended liveness cost**, stated here rather than discovered later.
- **Vault storage and ABI grow**: one immutable for the sandbox implementation, one mapping for per-proposal sandboxes carved from `__gap`, one new `onlyGovernor` function. The governor gains the sandbox fields on `StrategyProposal`. **BREAKING** for the vault/governor layout goldens; no live vault proxy exists, so no migration is required (see design.md "Deployment reality").
- **The owner is out of the loop entirely.** No `setAdapterAllowed`, no `setClassAllowed`, no `setTemplateApproval`, no certification. The only owner-adjacent fact left is that the sandbox implementation address is fixed at vault deploy, so replacing it is a protocol upgrade — not a per-proposal or per-venue decision.

## Capabilities

### New Capabilities
- `sandbox-execution`: per-proposal isolated execution of proposer-supplied arbitrary calls — funding, dispatch, the privileged-address denylist, settle-time sweep and approval teardown, residue reporting, and the structural max-loss bound that keeps tier-2 coverage sound.

### Modified Capabilities
- `tier-policy`: tier 2's "arbitrary calldata" becomes reachable with no owner action at all, via the sandbox path. The adapter-allowlist axis is unchanged and keeps gating batch callees; what changes is the stated rule that tier 2 is priced-and-reviewed rather than owner-admitted — the reviewing party for an arbitrary target is the guardian cohort at approval time, not the registry owner at listing time.
- `syndicate-vault`: a new governor-gated sandbox entry point that funds and dispatches a protocol-minted sandbox outside the batch guard, and records it for residue.
- `syndicate-governor`: sandbox calls become proposal data, stored at propose, readable before approval, and dispatched at execute under the same coverage and effective-capital scaling as the execute batch.

The execute-time funding bound stays a `sandbox-execution` requirement rather than a governor one, so this change can land before or after `per-call-capital-declarations` without either blocking the other.

## Impact

- **New**: `src/CallSandbox.sol` (the minted implementation), `src/interfaces/ICallSandbox.sol`.
- **Modified**: `src/SyndicateVault.sol` (sandbox implementation immutable, per-proposal sandbox mapping carved from `__gap`, the `onlyGovernor` entry point, residue recording), `src/SyndicateGovernor.sol` (sandbox call set + funding as proposal data, dispatch at execute, coverage contribution), `src/interfaces/ISyndicateVault.sol` and `ISyndicateGovernor.sol`. `src/TierRegistry.sol` natspec only — **no registry code or ABI change**.
- **Storage goldens**: `script/syndicate-vault-layout.golden.json` and `syndicate-governor-layout.golden.json` regenerate. Legal because no vault proxy is live.
- **Deploy**: `script/robinhood-mainnet/` deploys `CallSandbox` and passes it to the vault implementation constructor. **No registry ceremony of any kind.** `openspec/specs/deployment-docs` gains the ordering.
- **Operational**: `tier2CallCapBps` must be seeded to a real value — its inert default (`10_000` = 100% of TVL) makes sandbox funding unbounded, which is the one configuration in which this change is strictly worse than today.
- **Tests**: new sandbox suite (funding bound, denylist, sweep completeness, residue reporting, max-loss invariant, guardian-review readability); a pin asserting `_guardBatchCalls` still refuses a non-allowlisted callee named directly in a batch, so the sandbox is never mistaken for a relaxation of the batch guard.
- **Contract size**: `CallSandbox` is standalone; vault and governor growth is modest against Robinhood's 98,304-byte limit but must be measured, since the legacy Base vault has 18 bytes of headroom and is out of scope by standing decision.
- **Cross-references**: issue #166 (`target-based-batch-gating` — the gate this bypasses by not being a batch, rather than weakens), issue #18 (exotic-asset selectors), issue #115 / PR #157 (the four selector-enumeration rounds), pashov finding #15 (`_demote` clearing the allowlist — **no longer inherited**, since the sandbox holds no registry entry to demote).
