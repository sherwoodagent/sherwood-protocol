# Target-based gating of governor-batch sub-calls — Option B (issue #166)

## Why

**The selector allowlist in `SyndicateVault._guardBatchCalls` has been empirically demonstrated, four audit rounds running, to be un-completable.** Issue #115's remediation (PR #157) guarded 4 legacy ERC-20 selectors; a round-2 audit found 4 missed alternate-signature selectors (Permit2 `transferFrom`/`approve`, DSToken `pull`/`move`); round 3 found 4 more on the SAME routers round 2 had just "covered" (Permit2 batch `transferFrom`, DSToken `push`, ERC-1363 `transferFromAndCall`/`approveAndCall` + overloads); round 4 found 2 more, including a structurally new calldata shape (ERC-4626 `withdraw`/`redeem`, source arg at position 2 instead of 0). Three consecutive audit rounds each found real, exploitable gaps in the previous round's "complete" list — and issue #18's ERC-721/1155/777 selectors (`setApprovalForAll`, `safeTransferFrom`, `authorizeOperator`) are *known* to still be unguarded. The current guard's own natspec (src/SyndicateVault.sol:717-749, "COVERAGE IS PER-SELECTOR, NOT PER-ROUTER") concedes the point: every new token-router standard, and every overload of an existing one, is a new open door until someone manually finds and adds its selector. PR #157's audit recommended Option B — gate every batch sub-call by `target` against the TierRegistry, regardless of selector — as the durable fix in round 2, and every round since has deferred it as "required follow-up, not attempted in this round" (src/SyndicateVault.sol:639-652, :726-732). This change is that follow-up.

**Why target-gating closes the class.** Governor batches execute via `delegatecall`, so every sub-call reaches its target carrying `msg.sender == vault`. The selector allowlist tries to enumerate which *function shapes* can move value under that identity — an open-ended set. Target-gating inverts the question: instead of "is this calldata dangerous?", it asks "has the owner consented to this address being reachable with the vault's identity at all?" — a closed set the owner already curates. An unknown selector on an unknown target stops being a gap, because the unknown target is refused before the selector is ever examined. This also closes surfaces the selector guard never saw at all: raw ETH `value` transfers (a `Call` carries `value`, src/BatchExecutorLib.sol:19-23, and an empty-calldata value-bearing call to an arbitrary address is invisible to every selector check and to the `asset()`-only net-outflow meter), and every exotic-asset standard in issue #18.

**What target-gating does NOT close, stated honestly.** For a target that IS allowlisted — chiefly ERC-20 tokens the batch must legitimately call, like `asset()` or a reward token — an unguarded selector on that specific contract remains recipient-unchecked. That is why this change **retains** the existing selector layer as defense-in-depth rather than replacing it: the selector checks stop being the outer security boundary (where missing one selector = an open door on every token the vault holds) and become a second gate on the small, owner-attested set of allowlisted callees. The residual is bounded by governance discipline the spec now states explicitly: never allowlist an exotic-asset contract (NFT, 1155, 777) as a batch callee.

**Precedent.** Issue #118's landed fix (`SyndicateGovernor._rejectPrivilegedTargets`, src/SyndicateGovernor.sol:1055-1084, and the vault's Part 1 denylist) is this codebase's most recent, most-audited "gate by target" design: degrade-open when the predicate/registry cannot be resolved (a staticcall probe, never a typed call — fail-early must never become fail-always), fail-closed when it resolves and refuses. This change follows that pattern exactly on the vault's registry-gated half, and single-sources the new predicate on the registry's existing `isAdapterAllowed` rather than minting a second allowlist (the same no-restatement rule #118 applied to `isPrivilegedBatchTarget`).

## What Changes

- **`SyndicateVault._guardBatchCalls`** (src/SyndicateVault.sol:761-942): inside the existing registry-gated section (Part 2 — after Part 1/1b's unconditional guards and after the two degrade-open registry returns), add a **callee gate**: every sub-call's `target` must be either the vault's underlying `asset()` or an address for which `ITierRegistry(registry).isAdapterAllowed(target)` returns true; otherwise revert with a new error `DisallowedBatchCallee(target)`. The gate runs on every call regardless of selector or calldata length — including empty-calldata and ETH-`value` calls, which today bypass every selector check.
- **The selector layer is retained, not replaced.** Parts 1, 1b (unconditional privileged-target denylist and `transferFrom`-source guard) and Part 2's recipient/spender checks all keep running unchanged. Rationale in design.md Decision 3: on an allowlisted token target, `approve(attacker, max)` must still be recipient-refused; target-gating alone cannot do that.
- **`asset()` exemption on the callee gate** (design.md Decision 2): `target == asset()` skips the callee gate — every deploy batch must call `asset().approve(adapter, …)`, and the asset token is the one deployment-time-vetted contract whose balance the outer net-outflow meter independently verifies. Calls to `asset()` remain fully subject to Parts 1b and 2's selector checks. The existing recipient-side self-transfer fast-path (`recipient == vault && target == asset()`, src/SyndicateVault.sol:937) is preserved verbatim.
- **`ISyndicateVault`**: declare `error DisallowedBatchCallee(address target);` alongside the existing batch-guard errors.
- **`TierRegistry`**: **no code change.** `isAdapterAllowed` is reused as the callee predicate; its natspec (and the tier-policy spec) broaden its stated semantics from "may appear as spender/recipient of value-moving calls" to "may be reached by a governor batch at all, and hence may receive vault funds" — design.md Decision 1 argues these are the same consent under selector-blindness, which is why no second allowlist/axis is created. Codehash self-heal (issue #137) and demotion-clears-allowlist (issue #51 lineage) are inherited by the callee gate for free.
- **Propose-time validation is deliberately NOT extended** to the callee gate. #118's Decision 2 applies verbatim: `isAdapterAllowed` is mutable and codehash-sensitive state, so a propose-time pass proves nothing about execute/settle time and would manufacture false completeness. `propose` keeps checking the unconditional denylist half only.
- **Natspec debt paid**: the long-form comments that document Option B as "deferred / required follow-up" (src/SyndicateVault.sol:120-127, :639-652, :710-749) and the exotic-asset RESIDUAL note in `executeGovernorBatch` (:524-536) are rewritten to describe the landed two-layer model.
- **Tests**: a new callee-gate suite; the existing selector-guard suites are updated where they exercised recipient checks through *non-allowlisted* token targets (those now refuse earlier, at the callee gate — tests that still want to reach the recipient check must allowlist the token first, which also keeps the recipient layer honestly covered).

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `syndicate-vault`: new requirement "Target-based batch callee gate" (registry-gated, degrade-open on unresolved registry, fail-closed on resolved-and-refused; `asset()` exempt; selector layer retained beneath it).
- `tier-policy`: "Adapter allowlist is a separate axis from tiers" broadens the allowlist's stated consumption — it now also gates the callee of every governor-batch sub-call, with the accompanying governance-discipline rule (never allowlist exotic-asset contracts as callees) and the demotion/codehash-drift consequences extended to callability.

## Impact

- `src/SyndicateVault.sol` — callee gate inside `_guardBatchCalls`'s Part 2 loop; new error usage; comment rewrites. No storage changes. Bytecode growth trivial against Robinhood 4663's 98,304-byte limit (vault ~25.6 KB); the legacy Base vault (18 bytes headroom) cannot take upgrades and is out of scope by standing decision.
- `src/interfaces/ISyndicateVault.sol` — one new error declaration.
- `src/TierRegistry.sol` — natspec only (no ABI, no storage, no behavior change).
- `src/SyndicateGovernor.sol` — untouched.
- `test/vault/SelectorGuard.t.sol`, `test/vault/OutflowMetering.t.sol`, `test/audit-fixes/Vault_batchQueueTargets*.t.sol`, integration suites wiring a registry — updated per design.md's test-impact sweep; new `test/vault/CalleeGate.t.sol`.
- **Operational**: upgrade discipline for in-flight proposals (design.md Decision 3) — roll the vault implementation when a vault has no open proposal, or pre-allowlist the open proposal's stored targets; pre-populate `setAdapterAllowed` for every target live flows legitimately call before upgrading.
