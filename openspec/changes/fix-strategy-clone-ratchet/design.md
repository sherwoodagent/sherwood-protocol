# Design — bind strategy-clone execution to its owning proposal (issue #150)

All line references are against `origin/main` @ `00a264a`.

## Context

`BaseStrategy` is the abstract base every strategy template extends (`PortfolioStrategy`, `VeniceInferenceStrategy`; `MockStrategy` in tests). Clones of a template are deployed per proposal via `StrategyFactory.cloneAndInit` / `cloneAndInitDeterministic` (src/StrategyFactory.sol:123-133, :149-162) — ERC-1167 minimal proxies, initialized atomically, immutable thereafter. The lifecycle is a one-shot ratchet:

- `enum State { Pending, Executed, Settled }` (src/strategies/BaseStrategy.sol:39-43), stored per clone (`_state`, :47).
- `execute()` (:86-90): `onlyVault`; reverts `AlreadyExecuted` unless `_state == Pending`; flips to `Executed`; runs `_execute()`.
- `settle()` (:93-97): `onlyVault`; reverts `NotExecuted` unless `_state == Executed`; flips to `Settled`; runs `_settle()`.

The clone stores its vault and its deployer-proposer (`_vault`, `_proposer`, :45-46) — but **no proposal identity**. It cannot: clones are pre-deployed *before* the proposal that will use them exists (src/StrategyFactory.sol:30-36), so no `proposalId` is available at `initialize` time.

`propose` stores the declared clone address as `p.strategy` (src/SyndicateGovernor.sol:276) but never validates it (at the time of writing, src/StrategyFactory.sol natspec called its allowlist "the single chokepoint"; that claim was retired in SHE-209 / PR #284 — the `TierRegistry` class allowlist admits any clone of a class-allowed template, factory-made or not, and the vault binds each to itself. Either way the factory allowlist gates *templates*, not clone instances).

## Decision 1 — the authorization gap, named precisely

**The gap is a missing proposal-identity check, not a missing or wrong caller check.** `onlyVault` (src/strategies/BaseStrategy.sol:67-70) is present and correct as far as it goes: only the vault can call `execute()`. But the vault is a *shared execution muscle*: `executeGovernorBatch` delegatecalls `BatchExecutorLib.executeBatch` (src/SyndicateVault.sol:504-505), so every sub-call of every proposal's batch reaches its target with `msg.sender == vault`. The vault's batch guard deliberately exempts strategy entrypoints — they are the legitimate batch surface (src/SyndicateVault.sol:583-587) — and #118's propose-time check inherits exactly that two-address scope (`_rejectPrivilegedTargets`, src/SyndicateGovernor.sol:1055-1084, consuming `isPrivilegedBatchTarget`, src/SyndicateVault.sol:551-553 / :950).

So the answer to "who can call `execute()` on a clone" is today: **any registered agent who can get any proposal executed on that vault** — the batch contents are proposer-authored, `propose` only requires `vault.isAgent(msg.sender)` (src/SyndicateGovernor.sol:229), and neither the governor nor the vault nor the clone checks that the batch's proposal is the one the clone was deployed for. There was never a caller check that is "missing or wrong"; the *proposal-binding* check was never designed, because `IStrategy`'s lifecycle comment (src/interfaces/IStrategy.sol:15-21) assumes the agent's own proposal drives the clone and nothing enforces the assumption. Verified end-to-end by the PoC recorded on issue #150 (2026-08-03, post-#164).

## Decision 2 — the fix: the clone checks the governor's active proposal; no new state, no registry, no interface change

**Decision:** `execute()` requires that the clone is the declared strategy of the vault's currently-active proposal:

```solidity
// inside execute(), before the ratchet flip
address gov = IGovernorBinding(_vault).governor();          // ISyndicateVault:123 / SyndicateVault.sol:978-980
uint256 pid = IProposalStatus(gov).getActiveProposal();     // SyndicateGovernor.sol:888-890
if (IProposalStatus(gov).strategyOf(pid) != address(this)) revert NotActiveProposalStrategy();
```

`IProposalStatus` already exists and already carries exactly these two members (src/interfaces/IProposalStatus.sol:21-33); `IGovernorBinding` is a one-member local interface, following `VeniceInferenceStrategy`'s `ITierBindingPath` precedent for a strategy-side lookback (src/strategies/VeniceInferenceStrategy.sol:43). `pid == 0` (no active proposal) needs no special case: `strategyOf(0)` is `address(0) != address(this)`.

**Why this is sound — ordering proof against the governor's execute path.** `executeProposal` writes `_activeProposal = proposalId` (src/SyndicateGovernor.sol:378) and stamps `executedAt` (:390) *before* running the batch (:451, CEI); `p.strategy` was written at propose (:276) and is immutable for the proposal's lifetime. So during the legitimate execute batch, `getActiveProposal()` returns the driving proposal and `strategyOf(pid)` returns its declared clone — the check passes exactly when the batch targets the clone the proposal declared, and fails for every other clone. An unrelated proposal's batch calling a foreign clone's `execute()` hits `NotActiveProposalStrategy` and — because `BatchExecutorLib` bubbles sub-call reverts (src/SyndicateVault.sol:506-510) — fails its own execution wholesale, loudly, at the attacker's cost.

**Why not the issue's option 1 (governor/factory clone registry)?** Investigated and costed on the issue (2026-08-03 comment): `StrategyFactory` has no on-chain registry of clone instances — only `approvedTemplate` (implementation allowlist, src/StrategyFactory.sol:58) and an event. Option 1 requires new factory state (`isClone` mapping), a new invariant on a widely-used contract, a new propose-time loop in the governor, and migration reasoning for clones deployed under old factory state. Worse, it inherits #118's degrade-open posture by construction (propose-time checks in this repo degrade open — `_rejectPrivilegedTargets`'s capability probe, src/SyndicateGovernor.sol:1060-1064): a bricking-*prevention* check that degrades open protects nothing when it matters. Rejected.

**Why not the issue's option 2a (thread `proposalId` through `initialize`)?** Structurally impossible as stated: the proposalId does not exist when the clone is initialized (pre-deploy-then-propose is the documented order, src/StrategyFactory.sol:30-36). Making it possible means either a post-hoc `bindProposal` call from the governor at propose (new governor code, new clone entrypoint, new spoofing surface to authorize) or inverting the deploy order (breaks the deterministic-address propose flow, src/StrategyFactory.sol:136-148). Rejected.

**The chosen mechanism is the issue's option 2b** ("make the ratchet reject a call arriving before the clone's own proposal is active"), implemented with zero new state by reading the binding that already exists: the governor's proposal store is already the single source of truth for "which clone is active for this vault", and it is already exposed through the narrow `IProposalStatus` seam the vault itself consumes for the same question (`strategyOf(getActiveProposal())`, src/SyndicateVault.sol:1017-1021). This matches the #118 idiom — single-source the predicate, consumers ask rather than restate (design.md of `propose-time-target-validation`, Decision 1) — with the governor's proposal store as the predicate body. It also matches the #147 idiom of strategy-side enforcement through an existing walk (`_requireAllowedAdapter`'s `vault() → governor() → tierRegistry()`, src/strategies/VeniceInferenceStrategy.sol:247-286): the strategy defends itself using the wiring it already trusts, instead of asking two other contracts to grow new state.

**Fail-closed, not degrade-open — the deliberate inversion of #118's posture.** #118's propose-time check could degrade open because `_guardBatchCalls` remained the authoritative enforcement behind it. Here there is no second layer: this check IS the enforcement, so a capability-probe/skip pattern would reduce the fix to documentation. Typed external calls throughout; if `_vault` lacks `governor()`, or the governor lacks the views, or any hop reverts, `execute()` reverts. That is correct on both axes: (a) a clone that cannot verify its wiring must not pull capital from it; (b) the failure is recoverable (redeploy against correct wiring) while the failure it prevents is permanent (a flipped ratchet). The mixed-version worry that justified degrade-open in #118 does not exist here: the check ships inside new *templates*, every clone of a new template is new by definition, and current main's vault and governor already expose all three views — there is no legitimate pairing of a new clone with view-less infrastructure. (The Venice walk hardens each hop with raw length-checked staticcalls because it must classify *hostile* hop targets into a specific error; here every hop failure collapses into the same correct outcome — revert — so typed calls suffice.)

**`settle()` stays unguarded — argued, not assumed.** Two independent reasons:

1. *Transitive protection.* `settle()` requires `_state == Executed` (:94), which post-fix only the owning proposal's batch can set. While that proposal is open (Executed state), the single-open-proposal invariant (`_openProposalCount`, spec "Single open proposal per vault") means no other proposal can even be proposed; the only batches that can run are the owning proposal's own settlement (src/SyndicateGovernor.sol:473-474, batch before `_finishSettlement` at :476), its `unstick` replay (src/GovernorEmergency.sol:65, before the hook at :66), or its owner-proposed, guardian-reviewed emergency calls (src/GovernorEmergency.sol:114, before the hook at :115). Every path belongs to the owning proposal.
2. *Recovery is load-bearing.* If the owning proposal settles via owner-supplied emergency calls that bypass a broken clone, the clone is orphaned in `Executed` with position tokens still in custody. Today a later proposal's batch can call `settle()` on it and `_settle()` pushes the underlying back to the vault (`_pushToVault`/`_pushAllToVault`, src/strategies/BaseStrategy.sol:133-141) — funds flow to the vault, never to the caller. Guarding `settle()` with the active-proposal check would make orphaned clones permanently unsettleable and strand those funds. The residual "grief" of a foreign settle on an orphaned clone is that its `Executed → Settled` flip ends the (dead) proposer's `updateParams` access (:100-103) — on a strategy whose proposal is already terminal. Accepted.

**Residual risk, stated for the spec.** The check binds execution to *the active proposal's declaration*, not to the clone's deployer. A hostile registered agent can still name the victim's pre-deployed clone as their **own** proposal's `p.strategy` and drive `execute()` legitimately through that proposal. What the fix changes is the cost and visibility: the clone address is now publicly declared in a proposal that must survive the veto vote, guardian review, and a risk-scaled proposer bond — versus today's silent one-line batch entry in any proposal. The mismatch is also mechanically detectable at review time (`IStrategy(p.strategy).proposer() != proposal.proposer`). Closing it fully is the already-documented deferred governor-side check `IStrategy.proposer() == msg.sender` at propose (src/StrategyFactory.sol:110-122), which is out of scope here: it has its own recorded deferral rationale and it would break the factory-authorized owner-deploys/agent-proposes flow (`_authClone` accepts `vault.owner()`, src/StrategyFactory.sol:88-96). This change narrows #150 from "silent, incidental, unattributable" to "public, governance-gated, attributable" — the same trust surface as any other malicious proposal content.

## Decision 3 — storage layout: zero new state; the goldens convention does not apply to strategies

**No new storage anywhere.** The binding is derived at call time (three view calls); `BaseStrategy` gains one error and one local interface, no state variables. Subclass storage (`PortfolioStrategy`, `VeniceInferenceStrategy`) is untouched; `execute()` is non-virtual, so no subclass code changes either.

**The storage-layout-golden convention is confirmed not applicable.** `script/check-layout-goldens.sh:1-10` scopes itself to the five *proxy-upgraded* contracts (SyndicateGovernor beacon; SyndicateFactory, GuardianRegistry, StakedWood, SyndicateVault UUPS), whose layouts are frozen because an upgrade must land on live state. Strategy clones are ERC-1167 minimal proxies of an immutable template (`Clones.clone` / `cloneDeterministic`, src/StrategyFactory.sol:130, :159): no upgrade path exists, each clone's layout is fixed at deploy forever, and new template versions start fresh lineages. No golden exists for any strategy (`test/VaultLayoutPins.t.sol` / `test/GuardianRegistryLayoutPins.t.sol` are the only pin suites), and none is added. Even under a hypothetical layout-compat lens the change is trivially safe — zero storage delta — but the honest statement is that the constraint does not exist for this contract class.

## Decision 4 — retrofit: not needed, and for existing clones not possible; the fix gates future clones only

**Not possible for deployed clones**: an ERC-1167 clone's behavior is its template's, fixed at deploy. There is no mechanism to patch a live clone; the fix propagates by deploying updated templates and allowlisting them (`setTemplateApproval`, src/StrategyFactory.sol:81-84).

**Not needed either — broadcast sweep, same method as the Lane-A vault-proxy audit:**

- No `cloneAndInit` / `cloneAndInitDeterministic` transaction and no `StrategyCloned` event appears anywhere under `broadcast/` (repo-wide grep over all run JSONs). No clone has ever been deployed through `StrategyFactory` on any chain.
- The only on-chain strategy *instance* ever initialized is in `broadcast/CreateWstETHProposal.s.sol/8453/` — a raw `CREATE` plus a direct `initialize(address,address,bytes)` call on legacy Base, predating the factory flow. Legacy Base is out of scope by standing decision (Robinhood-only stack; the Base vault cannot take upgrades regardless).
- On Robinhood 4663, no vault proxy has ever been created (the Lane-A audit finding), and `cloneAndInit` requires a registered vault (`_authClone` → `vaultToSyndicate != 0`, src/StrategyFactory.sol:88-91) — so no clone *can* exist there. Broadcast dirs confirm: strategy-template deploys exist only for 8453/46630.

Consequence: no migration tasks, no dual-behavior window, no "old clones" carve-out in the spec. The template redeploy is part of ordinary (first) deployment, not a migration.

## Test impact

Sweep basis: every call site of `.execute()` on a `BaseStrategy`-derived contract in `test/`, plus every harness giving `MockStrategy` (test/mocks/MockStrategy.sol:22) a vault it later pranks.

- **New — the headline PoC test** (natural home: a new `test/audit-fixes/Strategy_cloneRatchetBinding.t.sol`, harness modeled on `Vault_batchQueueTargets_lifecycle.t.sol`): pre-deploy clone B via `StrategyFactory`; drive proposal P1 (strategy = clone A) whose `executeCalls` include `cloneB.execute()`; assert `executeProposal(P1)` reverts `NotActiveProposalStrategy` (bubbled through the batch); then propose P2 (strategy = clone B) and assert it executes and settles cleanly — the exact #150 brick, now impossible.
- **New — unit tests on the binding check**: owning proposal executes (check passes, ratchet flips once, second execute in-batch still `AlreadyExecuted`); no active proposal ⇒ direct pranked-vault `execute()` reverts `NotActiveProposalStrategy` (pid 0 path); vault without `governor()` / governor without the views ⇒ execute reverts (fail-closed pinned as deliberate).
- **New — orphan recovery pin**: clone in `Executed` whose proposal reached terminal state; a later proposal's batch calls `settle()`; assert funds return to the vault — pins the deliberate absence of a settle guard so a future "symmetry" refactor can't strand orphans without failing a test.
- **Existing suites**: harnesses that execute strategies through the real governor+vault lifecycle keep working unchanged (the binding holds by construction). Harnesses that `vm.prank(vault)` and call `execute()` directly against a mock vault break loudly unless the mock answers `governor()` and the governor answers the `IProposalStatus` views — each such site gets wired with the existing `MockProposalStatus` (referenced at src/interfaces/IProposalStatus.sol:10) or converted to assert the new revert. The implementation task enumerates sites by grep at fix time rather than pinning a list here that would rot.

## Risks

- **Test-harness blast radius** is the real cost of the change (see above). Mitigation: `MockStrategy`-based suites get one shared helper that wires vault→governor→active-proposal in the mock stack.
- **A future second "active-proposal" source.** The check trusts `getActiveProposal()`/`strategyOf()` as the single source of truth. If a future change adds a second execution lane that runs batches without setting `_activeProposal`, legitimate executes would start reverting — loudly and fail-closed, which is the acceptable direction. The spec states the coupling so such a change must revisit this requirement explicitly.
- **Reentrancy surface**: the three added calls are `view` staticcall-semantics reads into contracts the clone already trusts (`_vault` and its governor); no state, no callbacks, executed before the ratchet write but with no external value movement preceding them. No new reentrancy path.
- **Sequencing**: none — no pending change touches `BaseStrategy.execute()` (proposal.md, Sequencing).
