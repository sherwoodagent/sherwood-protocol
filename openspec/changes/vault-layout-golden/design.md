## Context

Issue #148, verified still valid and unclaimed against `origin/main` immediately before starting. `SyndicateVault` (`src/SyndicateVault.sol`) is a UUPS proxy — `_authorizeUpgrade` is factory-gated (grep confirms the only `_authorizeUpgrade` override in the file) — and the only proxy in this protocol holding user assets directly (LP deposits, via ERC-4626). Its storage section runs `src/SyndicateVault.sol:106-238`: fourteen scalar/mapping fields, several bit-packed pairs (`minBufferBps`/`minHoldingPeriod`/`instantExitFeeBps`; `_mgmtBase`/`_mgmtLastUpdate`; `_crystallizedMgmt`/`_crystallizedPerf`), two `EnumerableSet.AddressSet`s, two mappings, and a trailing `uint256[28] private __gap`. None of it is currently pinned by any test or CI gate — `script/check-layout-goldens.sh` covers `SyndicateGovernor`, `SyndicateFactory`, `GuardianRegistry`, and `StakedWood`, but not the vault.

## Goals / Non-Goals

**Goals:**
- Close the exact gap the issue names: a forge-level slot/offset pin test plus a golden-JSON CI gate for `SyndicateVault`, at parity with the four contracts already guarded.
- Zero `src/` changes — this is additive test/CI infrastructure only.
- Document the append-only / same-slot-placeholder convention for future field removal, in the same place the existing layout-pin files document it.

**Non-Goals:**
- No change to `SyndicateVault`'s actual storage layout, interface, or behavior.
- No new tooling beyond what `script/check-layout-goldens.sh` already provides (`check_contract`, `--update-golden`) — this change is a straight extension of an existing mechanism, not a new one.
- No attempt to retrofit a StakedWood-equivalent forge-level pin test for contracts other than the vault (issue #148 is scoped to the vault).

## Decisions

### Decision 1: Positive pins over zero-checks, matching the established pattern

`GuardianRegistryLayoutPinsTest`'s own history (see its header comment) shows why a zero-check is the wrong default: `test_layout_gapStartsAtSlot22` was asserted with the field above it WIRED specifically because an unwired zero-check would pass even if the field had moved. The vault test follows the same rule: every field gets a write (via a real setter where one exists, or `vm.store` at the compiler-reported slot where none does) and the assertion reads back the written sentinel, not merely "still zero."

### Decision 2: `vm.store` for fields with no reachable setter in a minimal fixture

Several vault fields (`_laneALockPid`, `lastDepositAt`, `_interimNetFlow`, the management-fee accrual triple, the crystallized-fee pair) are written only from deep inside `executeGovernorBatch` / `_deposit` / settlement paths that require a live governor, withdrawal queue, and strategy — standing up that whole stack in a layout-pin test would make the fixture heavy and coupled to unrelated subsystems, exactly the kind of coupling the existing two layout-pin files avoid (their fixtures are minimal: a bare proxy plus a couple of sentinel addresses). Writing directly via `vm.store` at the slot `forge inspect ... storageLayout` reports, then reading back through the field's own getter where one exists, keeps the fixture minimal while still proving the slot assumption is correct rather than merely self-consistent within the test.

### Decision 3: Golden filename `script/syndicate-vault-layout.golden.json`

Follows the exact naming convention of the four existing goldens (`<kebab-contract-name>-layout.golden.json`), so no new naming scheme is introduced.

### Decision 4: This is an initial baseline, not a re-baseline

Per the same "fresh deployment" reasoning `check-layout-goldens.sh`'s header already documents for `SyndicateGovernor`/`GuardianRegistry`/`StakedWood`: `chains/4663.json` records no vault lineage, so pinning the current layout as the golden carries no compatibility risk with a live proxy. From this baseline forward, the append-only rule applies — documented in the new test file's header, matching the existing two files' convention, rather than as a new standalone process doc (proportionate to the size of this change).

## Risks / Trade-offs

- [`vm.store`-only fields could pin the WRONG slot if the compiler layout is misread] → mitigated by reading the layout programmatically (`forge inspect SyndicateVault storageLayout --json`) while writing the test, and by cross-checking every field that has a public getter through that getter rather than trusting the raw slot number alone.
- [Bit-packed slots (three packed pairs) are easy to get wrong on offset] → same mitigation; the golden JSON itself (generated by the script, not hand-written) is the second, independent check on packing, since it comes straight from the compiler.

## Migration Plan

None — test/CI-only addition, no deploy or storage impact.
